# 工程边界与后续开发

当前采用模块化单体服务和独立客户端：原生微信小程序、Web前台、厂家后台、平台后台共用API。没有为演示引入十几个空服务。业务数据真实写SQLite；后续迁移云数据库和对象存储时保留接口契约，逐步替换存储实现。

| 模块 | 当前职责 | 故障时处理 |
| --- | --- | --- |
| 身份与审核 | 服务端会话、微信/手机适配、角色、认证申请与人工终审 | 未认证不解锁敏感资料，不用缓存伪造认证 |
| 内容与货源 | 发布、草稿、审核、六项筛选、订货会与CMS | 下架只影响对应记录，失败显示局部提示 |
| 客户与权益 | 主体隔离、日额度幂等、联系意向、线下开通 | 失败不伪记联系成功，不把意向计为已加微信 |
| 推荐 | 双塔训练、本站行为、标签与授权摘要 | 失败回退已审内容；合成样本不证明生产效果 |
| AI任务 | 能力匹配、服务端密钥和提示词、异步状态 | 显示失败并保留输入，不影响其他列表 |
| 资料拆解 | 分片、队列、Python子进程、按页拆卡 | 原件/分片保留，异常文档不拖垮整页 |
| 页面配置 | 字典、产地顺序、轮播、模块开关、版本与回退 | 校验失败不替换上一个有效配置 |

代码目录按业务职责划分，客户端不直接访问数据库。公开API不得返回密钥、session_key、系统提示词或他人私有原件。平台官方知识通过授权的回答过程使用，用户知识按本人或主体范围隔离；反馈不自动汇入公共训练集。

前台和后台会话独立：网页入口通过固定workspace区分，API通过`X-Qishu-Scope: front|back`传递上下文；服务端签发的Cookie和Bearer会话绑定对应scope。客户端声称back不代表获得后台权限，身份和授权仍由服务端核验。后台管理员身份通过授权会话投影，不把用户主体的前台角色改写为admin。

厂家资质材料是独立私有用途：营业执照、至少30秒场所视频、5张不同照片；视频由ffprobe读取实际媒体流，客户端时长只作提示。审核通过必须具备完整材料及人工电话回访“接通且一致”记录。店主继续使用执照审核流程。审核材料不得通过普通内容发布变为公开，审核员读取及回访操作留痕。

网页导航使用URL与历史栈；弹层先返回，列表恢复筛选和位置。小程序使用原生页面栈及系统返回。平台适配契约只复用业务能力，不能把微信授权或浏览器DOM直接复制到抖音/App。

目前支持捕获业务异常、功能开关、推荐和AI失败降级，以及独立资料解析进程。API共享一个Node进程和数据库，不等于所有进程级/基础设施故障都隔离。`deploy`模板把静态网页与API分离；将来的高负载解析和AI工作器可独立部署，不需重写前端业务。

原有静态Demo未覆盖。本工程不包含商品订单、货款支付或商品分账。同行圈与经营工具保留后续扩展边界，首发入口已收缩到本轮确认范围。
